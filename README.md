# foliant-client

TypeScript client for [Foliant](https://foliant.network): budgeted agent accounts, payment channels and pools, and paying x402 endpoints against a Foliant ledger node. The agent side of the [reference implementation](https://github.com/gazoy/concord), byte-compatible with it: keys, addresses, canonical hashing and signatures are tested against vectors produced by the Python code.

```bash
npm install foliant-client
```

```ts
import { Agent, KeyPair, LedgerNode, PayingClient, Policy } from "foliant-client";

const node = new LedgerNode("http://127.0.0.1:8402");           // python demo/serve.py in the reference repo
const agent = await Agent.register(node, KeyPair.generate(), KeyPair.generate(), new Policy(500, 200, 3600));
await node.faucet(agent.address, "USDC", 10_000);                // devnet only

const client = new PayingClient(agent, { defaultDeposit: 100 });
const r = await client.fetch("http://127.0.0.1:8402/infer", { method: "POST", body: "hello" });
// 402 answered with a signed pool update; r.status === 200; client.receipts[0] is the provider-signed receipt
```

The signer refuses to sign outside the account's policy (`PolicyViolation`); the ledger refuses again, and against every ancestor's policy in a crew, when a deposit is applied. Off-chain updates are bounded by the deposit they draw on, so a session of calls costs one deposit and one settlement.

`Agent.attach(node, accountId, signerKey)` operates an account that already exists, for example one an orchestrator delegated.

## Amounts

**Amounts are `bigint`.** The Python reference and the contracts carry them as arbitrary-precision
integers and `uint128`; a JavaScript `number` holds integers exactly only below 2^53
(9,007,199,254,740,992), which at 18 decimals is about 0.009 of a token. Carrying protocol
integers as `bigint` removes the ceiling: `Policy` amounts, `window_secs`, `expiry`, balances,
deposits, sequence numbers and ledger timestamps are all `bigint`, so no call site has to remember
which fields are safe to mix.

Two things follow for anyone reading or writing the wire:

- **Node responses are parsed with `parseJsonBig`, not `JSON.parse`.** `JSON.parse` of a policy the
  node sent as `1234567890123456789` yields `1234567890123456768`: the digits are gone before any
  of this library sees the object. `parseJsonBig` reads each integer from the literal as it was
  written. It needs Node 22 or later; on an older runtime it refuses a document that would lose
  digits rather than returning a rounded one.
- **Requests are serialised with `canonical`, not `JSON.stringify`.** `JSON.stringify` throws on a
  `bigint`, and `canonical` already writes the digits in the form the ledger hashes.

`canonical()` refuses a plain `number` outside the exact integer range rather than hashing it. A
double at 1e21 and above renders as `1e+21` where Python writes the digits, so the same policy
would otherwise hash to two different ids in the two implementations, and a channel update at that
scale would produce a signature the Python node could not verify. Both failures are now covered by
cross-language vectors in `tests/vectors.json` under `big_integers`, generated by
`foliant/crypto.py`.

### Migrating from 0.1.x

Pass `bigint` where you passed `number`:

```ts
const policy = new Policy(5n * 10n ** 18n, 10n ** 21n, 3600n);
await node.faucet(agent.address, "USDC", 10_000n);
const cid = await agent.openChannel(payee, "USDC", 100n);
await agent.payChannel(cid, 30n);
```

`Policy.fromDict` refuses an amount given as a `number` rather than coercing it: a number reaching
it is either already rounded or about to be, and accepting the small ones would hide the defect
until the first large one.
