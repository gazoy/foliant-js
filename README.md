# foliant-client

TypeScript client for [Foliant](https://foliant.network): budgeted agent accounts, payment channels and pools, and paying x402 endpoints against a Foliant ledger node. The agent side of the [reference implementation](https://github.com/gazoy/concord), byte-compatible with it: keys, addresses, canonical hashing and signatures are tested against vectors produced by the Python code.

```bash
npm install foliant-client
```

Node 22 or later (`engines`): reading a node's response without rounding it needs `JSON.parse`'s
reviver source argument, which arrived in 22. See **Amounts** below for what happens without it.

```ts
import { Agent, KeyPair, LedgerNode, PayingClient, Policy } from "foliant-client";

const node = new LedgerNode("http://127.0.0.1:8402");           // python demo/serve.py in the reference repo
const agent = await Agent.register(node, KeyPair.generate(), KeyPair.generate(), new Policy(500n, 200n, 3600n));
await node.faucet(agent.address, "USDC", 10_000n);               // devnet only

const client = new PayingClient(agent, { defaultDeposit: 100n });
const r = await client.fetch("http://127.0.0.1:8402/infer", { method: "POST", body: "hello" });
// 402 answered with a signed pool update; r.status === 200; client.receipts[0] is the provider-signed receipt
```

The signer refuses to sign outside the account's policy (`PolicyViolation`); the ledger refuses again, and against every ancestor's policy in a crew, when a deposit is applied. Off-chain updates are bounded by the deposit they draw on, so a session of calls costs one deposit and one settlement.

`Agent.attach(node, accountId, signerKey)` operates an account that already exists, for example one an orchestrator delegated.

## Amounts

**Amounts are `bigint`.** The Python reference and the contracts carry them as arbitrary-precision
integers and `uint128`; a JavaScript `number` holds integers exactly only below 2^53
(9,007,199,254,740,992), which at 18 decimals is about 0.009 of a token. Carrying protocol
integers as `bigint` removes the ceiling: `Policy` amounts, `window_secs`, `expiry`, balances,
deposits, sequence numbers and ledger timestamps are all `bigint`, so no call site has to remember
which fields are safe to mix.

Two things follow for anyone reading or writing the wire:

- **Node responses are parsed with `parseJsonBig`, not `JSON.parse`.** `JSON.parse` of a policy the
  node sent as `1234567890123456789` yields `1234567890123456768`: the digits are gone before any
  of this library sees the object. `parseJsonBig` reads each integer from the literal as it was
  written. A number literal that is not plain digits (`1e30`, `1.0`, `1e400`) is refused rather
  than kept: Python writes an `int` as plain digits, so such a literal did not come from the
  reference, and none of them survives the round trip — `1e30` is not 10^30 once it is a double,
  `1.0` would have to be re-emitted as `1.0` to hash the way Python hashes it, and `1e400` is
  `Infinity`, which compares false against every `bigint`. A genuine fraction is left alone, and
  `canonical` refuses it in turn.
- **Requests are serialised with `canonical`, not `JSON.stringify`.** `JSON.stringify` throws on a
  `bigint`, and `canonical` already writes the digits in the form the ledger hashes.

`canonical()` refuses a plain `number`, at every magnitude, rather than hashing it. Python's
`json.dumps` writes an `int` as `1` and a `float` as `1.0` — different bytes, so a different hash
and a different signature — and JavaScript has one numeric type in which `1` and `1.0` are the same
value, so there is nothing in a number to tell the two apart. Above 2^53 the digits are gone as
well, and above 1e21 a double renders as `1e+21` where Python writes digits, so the same policy
would hash to two different ids in the two implementations and a channel update at that scale would
produce a signature the Python node could not verify. Those failures are covered by cross-language
vectors in `tests/vectors.json` under `big_integers`, generated by `foliant/crypto.py`.

### On a runtime older than Node 22

`parseJsonBig` has no exact path there — `JSON.parse` rounds the literal before any reviver can see
it — and no sound inexact one either, so **every call throws**. A scan can tell which literals
`JSON.parse` would misread, but the integers in a document it admitted would still come back as
`number`, which is not what this package's types say. That is an unsupported runtime rather than a
degraded mode, which is what `engines` declares.

0.1.x tried to serve it with a digit-run test over the raw document, and that was wrong in both
directions: it fired on digits inside strings and on object keys, so an ordinary
`/ledger/accounts/{id}` response was refused about one time in 740 on its hex ids alone, and every
response for an account whose policy amounts have 16 or more digits was refused outright — while
`1e30` and `12345678901234567890e0`, which really do lose digits, went straight through.

### One deliberate divergence from the reference

`escalation` may be `null`, an address string, or a key reference. The Python reference returns any
other truthy value unchanged, so a policy carrying `escalation: 7` loads there and the node will
store and serve it; this client refuses it with a `PolicyViolation`. The schema admits only those
three forms, and a co-signer that is not a key can never satisfy the ledger's signer comparison, so
nothing a conformant node meant is being refused — but it does mean this client cannot attach to an
account whose stored policy carries such a value.

### Migrating from 0.1.x

Pass `bigint` where you passed `number`:

```ts
const policy = new Policy(5n * 10n ** 18n, 10n ** 21n, 3600n);
await node.faucet(agent.address, "USDC", 10_000n);
const cid = await agent.openChannel(payee, "USDC", 100n);
await agent.payChannel(cid, 30n);
```

`Policy.fromDict` and the `Policy` constructor refuse an amount given as a `number` rather than
coercing it: a number reaching them is either already rounded or about to be, and accepting the
small ones would hide the defect until the first large one.

## Policy validity

A policy is checked against spec §2 wherever it enters — the constructor, `fromDict`, and so
`Agent.attach` and every `refresh` — because the signer exists so that the enclave does not take
the node's word for the policy it is enforcing. `per_tx_max` and `per_window_max` are bounded to
`[0, 2^128)`, `window_secs` to `[1, 2592000]` and `expiry` to `[1, 2^64 - 1]`, matching the Python
reference's documented bounds; addresses in the allow and deny lists, and a payee passed to
`check`, are canonicalised (§2.1: an EVM address compares in lowercase); and `escalation` may be a
key reference, an address, or `null`. Anything else is a `PolicyViolation`.

## Tests

`npm test` runs the cross-language vectors, the specification's own conformance vectors
(`docs/spec/vectors.json`, kinds `check` and `policy`), and an end-to-end test that starts the
Python node (`python demo/serve.py`). Both the vectors and the node come from a checkout of the
reference repo at `/home/claude/concord`; set `FOLIANT_REF` to point elsewhere. `npx tsc --noEmit`
type-checks the tests along with the sources.
